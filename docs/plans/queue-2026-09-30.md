**Attach pass (the part the spawner cannot do).** New store method `attachPendingClientNotes({ clientId? })` (both backends), idempotent, cheap when nothing is pending:
- Load pending notes with `attached_checklist_id is null`.
- For each, find the client's checklists with `templateId === note.templateId`, not deleted, not skipped, whose `createdAt > note.createdAt` (fallback when `createdAt` is missing: `dueDate > note.createdAt`'s date); pick the earliest by dueDate. That is "the next one that populates".
- kind `task`: insert an item on that checklist with id `item-pn-<noteId8>` (idempotent: `on conflict do nothing` on Postgres, skip-if-present on file), label = body, done false, at the END of the first stage's items; then stamp the note attached (checklist id, item id, attachedAt) in the same transaction on Postgres.
- kind `note`: stamp the note attached with the checklist id only. Checklists have no notes field, so the note is SHOWN by the checklist UI from this table (below).
- Call sites: at the end of `read()` after the materializer's guarded write-back SUCCEEDS (both backends), after the bulk `write()` (owner PUT), and after `generateChecklistFromTemplate`. Never inside `materializeRecurringChecklists` (pure; output may not persist).

**Routes.** `GET /api/clients/:id/pending-notes` (visible-client gate) returns pending AND attached (last 90 days) so the count and history render; `POST /api/clients/:id/pending-notes` `{ templateId, kind, body }` (JSON, origin, write gate above) -> 201 with the note; `DELETE /api/clients/:id/pending-notes/:noteId` (owner, or the author while still unattached). `GET /api/checklists/:id/pending-notes` (checklist visible) returns the notes attached to that checklist (kind note, and kind task for the link back). `api.ts` wrappers + types.

### C2. Push moves only the open steps; the done steps stay as a completed record (featreq-fbab3370)
Reading of her acceptance ("pushing a checklist where every item is completed pushes no items and moves all of them to Complete"): a push closes out what is done and carries only the open work to the new date.
- Store `pushChecklistInstance(id, { newDueDate, actorId })` (db/store.js ~19556) becomes:

  - every step done: refuse with a typed error the route maps to 409 `NOTHING_TO_PUSH` ("Everything here is done. Nothing to push."); the UI hides Push on a complete checklist;

Create a new checklist (new id) copying title, clientId, templateId, stageId / stageIndex / stageCount, caseId, categoryId, assigneeId, viewerIds / editorIds, periodLabel, frequency, with `cycleDueDate = coalesce(original.cycleDueDate, original.dueDate)`, `dueDate = newDueDate`, `pushedAt / pushedBy`, and a new field `pushedFromChecklistId = original.id`. The original keeps only its done steps, so it is complete and shows on the Completed tab; it also gets `pushedAt / pushedBy` (the "Pushed" flag) and `pushedToChecklistId`. One transaction on Postgres; one write on the file backend.
  - The push route (server.js ~9472) records the skip-ledger `push` entry against the NEW checklist id when a split happened, so next-occurrence rules and `checklist-push-next-occurrence.test.ts` keep their meaning (identity via `cycleDueDate`).   - Both backends: new nullable text columns `pushed_from_checklist_id` and `pushed_to_checklist_id` (added in `initialize()` like `pushed_at`), file fields of the same names; the bulk save preserves them like the push stamps (~7781); `mapChecklistRow` and the SELECT list carry them; the `Checklist` type gains `pushedFromChecklistId?` / `pushedToChecklistId?`.
