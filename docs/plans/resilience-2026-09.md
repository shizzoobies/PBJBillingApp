# Resilience — a failover you can flip, and the backups that matter more

**Written** 2026-09-03, the evening every Railway deploy failed for two hours
(npm 10.9.8 crashed on a registry change — `docs/HANDOFF.md` §5 that date).
Alex chose **Tier 1 + Tier 2** from the workshop: deterministic builds and
real backups first, then the same app on a second host behind Cloudflare
failover. Tier 3 (a Cloudflare-native port) was scoped and declined as a
*migration* decision, not a backup one.

## 0. What today's incident was, and was not

Production never went down — Railway kept serving the last good image. The
*deploy pipeline* broke. A standby site would not have helped unless it could
be deployed to, and its build would have hit the same npm bug. So the first
tier is about making builds deterministic; the second is about the failure
we did NOT have today (the host itself dying). The database is the single
point of failure no app-layer standby fixes — which is why backups are Tier 1
and failover is Tier 2, not the other way round.

## 1. Facts the plan rests on (verified 2026-09-03)

- `pbjsa.com` DNS is on **Cloudflare** (`melnicoff` / `carlane` nameservers);
  `app.pbjsa.com` is a **DNS-only CNAME** to `voexwunf.up.railway.app`.
- **Why the lockfile is gitignored:** commit `a2e6afe` (2026-04-30) — a
  `package-lock.json` generated on Windows lacked the Linux native optional
  deps (esbuild / rolldown bindings), so Railway's Linux install failed. The
  rule solved a real problem; the fix is to generate the lockfile on Linux.
- **No Dockerfile.** Railway builds with Railpack (Node 22, npm 10.9.8 —
  the version that crashed). Build currently depends on the service variable
  `RAILPACK_INSTALL_CMD` (npm 11), which lives only in the dashboard.
- **`/health` is a liveness check, not a readiness check**: it returns 200 with
  `mode`/`stripe` fields and never touches the database.
- 17 environment variables define a running instance (Railway's own aside):
  `ADMIN_EMAIL, ANTHROPIC_API_KEY, APP_PUBLIC_URL, DATABASE_URL,
  ELEVENLABS_AGENT_ID, ELEVENLABS_API_KEY, ELEVENLABS_WEBHOOK_SECRET,
  EMAIL_FROM, INVOICE_EMAIL_FROM, JWT_SECRET, NODE_ENV,
  OWNER_BOOTSTRAP_PASSWORD, OWNER_EMAIL, RESEND_API_KEY, STRIPE_SECRET_KEY,
  STRIPE_WEBHOOK_SECRET, VOICE_TOOL_SECRET`.
- Sessions, rate-limit state and SSE fan-out: sessions are in Postgres
  (survive a host switch); the rate limiter, pending-action stores and the SSE
  client set are **in-process memory** — so the standby must be
  **active/passive**, never active/active, or two hosts would each hold half
  the SSE clients and `broadcastDataChanged` would reach only some tabs.
- The weekly digest (`setInterval`) and the recurring-checklist materializer
  both run in-process; both are idempotent by design (a DB marker gates the
  digest; the materializer write-back is `expectedVersion`-guarded), so a
  passive host running them too is safe. Noted, not assumed — pinned by the
  existing tests for each.

## 2. Tier 1 — deterministic builds and real backups (hours)

### 2.1 `Dockerfile` in the repo (pins Node AND npm)
Multi-stage: `node:22-bookworm-slim`, `npm i -g npm@11.6.2` (or newer), copy
`package.json` + lockfile, `npm ci`, `npm run build`, then a runtime stage
with `--omit=dev`. Railway can build from it (set the builder to Dockerfile in
`railway.json`), which **retires `RAILPACK_INSTALL_CMD`** and removes the
dashboard-only dependency. The same image is what Tier 2 deploys elsewhere —
one artifact, every host.

### 2.2 The lockfile, generated on Linux
Lift the rule with the original problem actually solved: generate
`package-lock.json` **on Linux** so it carries the linux-x64 optional deps
(GitHub Actions `ubuntu-latest` running `npm install --package-lock-only`, or
the Dockerfile build itself). Remove `package-lock.json` from `.gitignore`,
commit the Linux-generated file, and switch install to `npm ci`. Windows
developers keep working: npm reads a lockfile that includes their platform's
optionals too when generated by npm ≥ 10 with all platforms' metadata —
verify by running `npm ci` here on Windows before declaring it done. **This
is the single change that would have prevented today.** The 2026-04-30
memory/rule gets rewritten to "lockfile is committed; regenerate on Linux".

### 2.3 Nightly `pg_dump` to Cloudflare R2, with a restore drill
A GitHub Actions cron (free) runs `pg_dump --format=custom` against
`DATABASE_PUBLIC_URL` and uploads to an R2 bucket via its S3 API; keep 30
daily + 12 monthly. **A backup that has never been restored is a hope, not a
backup**: the first run includes a restore into a throwaway Postgres and a row
count comparison, written up in the handoff. Owner-provided: the R2 bucket and
an R2 API token (names only in the repo; values in Actions secrets).
Also: confirm in the Railway dashboard whether Postgres volume backups are on
(they are a paid feature and are not a substitute for a restorable dump).

### 2.4 `/health` becomes a readiness check
`SELECT 1` against the pool with a short timeout; **503** when it fails,
keeping the existing 200 body otherwise. This is what lets a load balancer
tell "process alive" from "can serve". Railway's own healthcheck uses the same
path, so a DB-down deploy would now correctly fail rather than "succeed" into
a broken instance — a behavior change to be aware of, and the right one.

### 2.5 Uptime alerts to Alex's phone
Cloudflare Health Checks on `https://app.pbjsa.com/health` (the zone is
already there) with email/notification; a free external monitor (Betterstack
or similar) as the second opinion, since a Cloudflare-side issue would blind
Cloudflare's own checks.

### 2.6 A written rollback procedure
Railway keeps every previous SUCCESS image; the dashboard can redeploy any of
them in seconds. Document the exact clicks in the handoff §3 so the next
session reaches for it before debugging — today it took me two hours to
remember that production was never actually at risk.

## 3. Tier 2 — the flip (a day or two, same code)

- **Second host running the Tier-1 Dockerfile**, pointed at the SAME Railway
  Postgres over its public URL with SSL. Recommendation: Fly.io (Docker-native,
  `fly deploy` from the same image, cheap always-on machine). Render works the
  same way. A second Railway region is NOT a good standby — same provider,
  correlated failures (today's was Railway's builder).
- Replicate the 17 variables (`APP_PUBLIC_URL` stays `https://app.pbjsa.com`
  on both — the public name must not change on failover, or every deep link,
  Stripe webhook and voice-tool callback breaks).
- **Cloudflare Load Balancer** on `app.pbjsa.com`: proxied (orange cloud), two
  origins, Railway primary / standby secondary, **active-passive with health
  monitors on `/health`** (the Tier-1 readiness version). Failover is
  automatic; fail-back too. Cost is roughly $5–10/month — confirm in the
  dashboard. Proxying also means Cloudflare's WAF/rate-limiting sits in front
  of the app for free.
- Stripe and ElevenLabs webhooks already target `app.pbjsa.com`, so they
  follow the failover; the signing secrets are in both hosts' env.
- Quarterly drill: stop the Railway service for five minutes, watch the LB
  fail over, confirm a sign-in and an invoice PDF on the standby, start
  Railway, watch it fail back. Written into the handoff as a ritual.

## 4. Order of work

1. Dockerfile + Linux-generated lockfile + `npm ci` (one commit; Railway
   builds from the Dockerfile; retire `RAILPACK_INSTALL_CMD`).
2. `/health` readiness + tests (both backends: file mode reports ok).
3. GitHub Actions: nightly pg_dump → R2, with the restore drill on first run.
4. Cloudflare Health Checks + external monitor + rollback procedure in §3.
5. Standby host from the same image; Cloudflare LB active-passive; failover
   drill; handoff entry.

## 6. Explicitly not in scope

A Cloudflare Workers port of the app (Tier 3). Verified 2026-09-03 that
Workers now run `http.createServer` via `httpServerHandler`
(`enable_nodejs_http_server_modules`, compat date ≥ 2025-09-01), which would
spare the 10k-line router — but the in-process SSE set, timers, rate limiter,
pending-action stores, `pdfkit` streams and Stripe raw-body handling each need
their own Workers primitive, and every feature would then ship to two runtimes
forever. Revisit only as a decision to leave Railway.
